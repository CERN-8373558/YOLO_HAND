# E2 架构设计：手语拼音补全系统（工具层 + Agent + RAG 三层）

> 输入：手语打字机（camera_text.py）输出的**连续字母串**
> 输出：候选中文词/句 + 用户选择 → 落到文字缓冲
> 原则：三层低耦合，每层可独立测试/替换（对应方案文档"小而美"模块化）

---

## 1. 总体分层

```
┌─────────────────────────────────────────────┐
│              界面层 (UI)                     │  显示候选栏、接收用户选择
│        camera_text.py 扩展 / ui.py           │
└──────────────────────┬──────────────────────┘
                       │ 请求补全 / 回传选择
┌──────────────────────▼──────────────────────┐
│            Agent 决策引擎 (agent.py)          │  大脑：调度、歧义处理、确认流程
│  · 判断何时补全 / 是否够确定 / 要不要问用户     │
│  · 决策失败时决定调用 RAG 还是请求用户          │
└──────┬──────────────┬───────────────┬────────┘
       │ 工具调用       │ 工具调用       │ 语义检索(按需)
┌──────▼───────┐ ┌─────▼──────┐ ┌─────▼─────────┐
│ 工具层        │ │ 工具层      │ │ RAG 增强层      │
│ tool_dict.py │ │ tool_seg.py │ │ rag.py         │
│ 拼音→汉字表   │ │ 切分器+Viterbi│ │ 向量库+检索    │
│ tool_lm.py   │ │ tool_cand.py│ │ (Faiss/Chroma) │
│ n-gram 打分   │ │ Top-N 汇总  │ │ 语义候选/纠错   │
└──────────────┘ └────────────┘ └────────────────┘
```

依赖方向：**UI → Agent → 工具层/RAG**（单向），工具层/RAG 不反向依赖上层。

> 术语说明：方案文档里的"MCP（模块控制平面）"思想 = 把模块能力封装成统一接口、便于上层调用。本系统用"**工具层（Tool Layer）**"实现该思想，是**系统内部能力层**，与标准 MCP 协议（Model Context Protocol，LLM 调外部工具的标准）无关。

## 2. 一次完整补全的数据流（时序）

场景：用户打完 `nihao`，系统要给出候选。

```
[UI] 字母流稳定="nihao"（检测到停顿/收手）
  │
  ▼
[Agent] decide("nihao", context="")
  │   ① 先调本地工具试试（快）
  ▼
[tool] tool_seg.pinyin_cut("nihao")
  → 切分路径: ni|hao (得分 0.9), nian|hao(0.1), ...
  ▼
[tool] tool_dict.expand("ni") → 你/泥/尼;  expand("hao") → 好/号/豪
  ▼
[tool] tool_lm.score([你,好]) = 0.95   score([你,号]) = 0.01
  ▼
[Agent] 汇总 → 最高候选 [你好 0.95] [泥号 0.0X]...
  │   ② 决策：最高分够不够高？
  ├─ 是(score≥阈值) → 直接输出候选[你好]→ UI 显示，1 键确认
  ├─ 否但次选也不差 → 标记"歧义"，UI 显示候选列表等用户选 (2/3/4)
  └─ 全部低分(疑似识别错/词不在库) → 转 ③
  ▼ ③ 调 RAG
[RAG] retrieve("nihao", 上文) → 向量检索最近语料/常用句
  → 返回语义更合理的候选/纠错建议 [你好] [您好] [泥好?请确认]
  ▼
[Agent] 拿 RAG 结果重新决策 → 输出最终候选
  ▼
[UI] 候选栏: 1.你好 2.您好 3.泥嚎   ← 用户按数字键选择
  → 选中文本 append 到 TextBuffer → 继续打下一词
```

## 3. 工具层：接口定义（4 个工具）

统一工具约定：每个工具是纯函数，**输入输出都是普通 JSON 兼容结构**，方便 Agent 调用、也方便后续换成独立服务 / MCP Server / HTTP 服务。

### 工具 1 `tool_seg.pinyin_cut(letters) -> [Segments]`
把字母串切成合法拼音音节，带路径得分。
```json
入参: {"letters": "nihao"}
出参: {
  "segments": [
    {"syllables": ["ni","hao"], "score": 0.90, "coverage": 1.0},
    {"syllables": ["nian","hao"], "score": 0.10, "coverage": 1.0},
    {"syllables": ["n","i","h","a","o"], "score": 0.01, "coverage": 1.0}
  ]
}
```
实现要点：全切分（枚举所有合法切分）+ Viterbi/DP 按 LM 打分取 Top 路径。

### 工具 2 `tool_dict.expand(syllable) -> [CharCand]`
单个音节的同音候选。
```json
入参: {"syllable": "ni"}
出参: {"candidates": [
  {"char": "你", "freq": 0.91},
  {"char": "泥", "freq": 0.02},
  {"char": "尼", "freq": 0.01}
]}
```

### 工具 3 `tool_lm.score_sequence(word_seq) -> float`
给一个候选词序列打分（bigram/trigram 连乘，含平滑）。
```json
入参: {"words": ["你","好"]}
出参: {"score": 0.95, "logprob": -0.02, "source": "bigram"}
```

### 工具 4 `tool_cand.build(letters, top_k=5) -> [Candidate]`
组合工具1/2/3，给出整串的 Top-N 完整候选（**Agent 主要消费这个**）。
```json
出参: {"candidates": [
  {"text": "你好", "score": 0.95, "conf": 0.9, "seg": "ni|hao", "source": "local"},
  {"text": "泥好", "score": 0.01, "conf": 0.1, "seg": "ni|hao", "source": "local"}
], "best": "你好", "ambiguous": false}
```

> 注：tool_cand 是"便捷聚合工具"，Agent 多数时候调它即可；细分工具保留给需要深入排查的场景（高内聚 + 接口完整）。

## 4. Agent 决策引擎：状态与规则

Agent 持有一个**决策上下文**，输入：当前字母串 + 候选结果 + 上文。

```
decide(letters, context) -> action
```

规则优先级（参考方案文档 Agent 逻辑）：

| # | 条件 | 决策 | 说明 |
|---|------|------|------|
| 1 | 字母串太短(<2) 或 正在输入中 | `defer` | 不动，等收手/停顿 |
| 2 | best.score ≥ 0.8 | `output(best)` | 足够确定，直接出第一候选 |
| 3 | 最高两名得分接近(差<0.1) | `confirm(candidates)` | **歧义** → 显示列表等用户选 |
| 4 | 全部候选 score < 0.5 | `ask_rag(letters)` | **都不像** → 调 RAG 重排/纠错 |
| 5 | RAG 返回后仍低 | `confirm` + 提示"无法识别" | 给用户机会确认或删掉 |
| 6 | 识别置信度低(手语帧 conf<0.7) | 优先走 4 | 怀疑字母本身有错，先纠错 |

阈值做成参数，方便 E12 调优：
```json
{"output_th": 0.8, "ambig_gap": 0.1, "rag_th": 0.5, "hand_conf": 0.7}
```

## 5. RAG 增强层：接口与数据

RAG 不是每次都调（避免慢），只有 Agent 判定"本地候选全都不好"才触发。

### 接口 `rag.retrieve(query, context, top_k=3)`
```json
入参: {"query": "nihao", "context": "我想吃"}
出参: {
  "hits": [
    {"text": "你好", "similarity": 0.93, "source": "corpus"},
    {"text": "泥好", "similarity": 0.88, "source": "history"},
    {"text": "您号", "similarity": 0.82, "source": "corpus"}
  ],
  "suggestion": "你好"
}
```

### RAG 的数据源（3 类，都进向量库）
| 来源 | 内容 | 用途 |
|------|------|------|
| 常用语料库 | 常见短语/句子（E3 语料切句） | 通用补全/纠错 |
| 用户历史 | 用户之前打过的句子 | 个性化（句意连贯） |
| 场景语料(可选) | 如医疗/教育专用词 | 场景适配 |

### 向量化
- 简单版：把**整句候选**文本 embedding 后比对
- 若接大模型 API：可用 embedding 模型（如 text-embedding）做向量，或直接用 LLM 重排
- 本地无 embedding 时：先用**字面编辑距离 + 词频加权**做弱 RAG（不需要模型，快）

> 设计决策：**RAG 与工具层的"纠错"能力部分重叠**。初版建议 RAG 只做"候选重排/提语义合理项"，纠错主责在切分器(Viterbi 容忍错字母)。

## 6. UI 交互（E10 时细化）

候选栏放在摄像头窗口顶部（输入框下方第二行）：
```
文本区:  你好|
候选栏:  1.你好  2.您好  3.泥嚎
按键:   数字1-9选候选 | ←/→ 翻页 | c清空 | q退出
```

Agent 出 `confirm` 时候选栏激活；出 `output` 时高亮第一候选（可空格快速确认）。

## 7. 模块与文件规划（高内聚低耦合）

```
yolo_demo/
├── pinyin_/
│   ├── __init__.py
│   ├── dict_data.py      # 拼音→汉字表 + 词频 (E3)
│   ├── tool_seg.py       # E5 切分器
│   ├── tool_dict.py      # E4 拼音→字表接口
│   ├── tool_lm.py        # E6 n-gram 打分
│   ├── tool_cand.py      # E7 Top-N 聚合
│   ├── agent.py          # E8 决策引擎
│   ├── rag.py            # E9 向量检索增强
│   └── ui_candidates.py  # E10 候选栏组件
└── camera_text.py        # 接入补全（UI 层集成）
```

测试依赖顺序：E4→E5→E6→E7（工具层单测）→ E8（Agent 用假工具测）→ E9 → E10（UI）→ E11 端到端。

## 8. 风险与对策

| 风险 | 对策 |
|------|------|
| n-gram 语料不足、候选瞎猜 | E3 用现成词库 + 平滑；RAG 兜底 |
| 每字母都触发补全 → 卡顿 | Agent 只在"停顿/收手"触发（E8 defer 规则1） |
| 中英无法区分 | 加中/英模式开关（UI 层），E11 前完成 |
| RAG 查询慢 | 按需触发 + 本地弱 RAG 起步 + top_k 限制 |
| 手语错字母(如 N→M) | 切分器纠错容忍 + Agent 低置信度走 RAG |
